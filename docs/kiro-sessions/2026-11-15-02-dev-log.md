## Prompt given to Kiro

````markdown
Set up development notes for the Kiroween hackathon submission and keep them up to date from now on.

Why: the judges score "Technological Implementation" on how well Kiro was used, and the submission must explain how Kiro was used (specs, hooks, steering, MCP, agents, vibe coding). We need a truthful, dated record of that while we build, not reconstructed at the end.

1. Create docs/KIRO_LOG.md with this structure:
   - Short intro: what Night Shift is (one paragraph) and that this file records how Kiro was used to build it.
   - "Kiro features in this repo": a table with one row per feature actually present in .kiro/ (steering files, specs, hooks, settings/mcp.json servers, custom agents). For each: the file path, what it does, and one concrete example of where it changed the result (e.g. the validate-bug-pack hook rejects a pack whose tests do not fail on the broken code). Only list things that really exist in the repo.
   - "Timeline": one entry per meaningful step, newest last. Backfill it now from `git log` (dates, commit hashes, what changed, which Kiro feature was used). Format per entry:
     ### YYYY-MM-DD — <title>
     - What: ...
     - Kiro feature: spec / hook / steering / agent / MCP / vibe coding
     - How Kiro helped: ... (what Kiro generated, what it caught, what was corrected by hand)
     - Problems and fixes: ...
     - Commit: <hash>
   - "Decisions": a short list of design decisions and their reasons (for example: Monaco lazy-loaded in its own chunk; bug packs are data validated by a hook; monster behaviour mirrors the bug).
   - "Metrics": numbers we can show judges, kept current: number of bug packs, number of unit tests, specs count, hooks count, bundle sizes from the last `npm run build` (gzip sizes of the main chunks).
   - "Open issues / next steps".
   Write it in English. Be factual: do not invent features, numbers or events. If something is unknown, write "TBD".

2. Create a steering file .kiro/steering/dev-log.md with front-matter `inclusion: always` that tells Kiro: after finishing any task that changes code, specs, hooks, steering or assets, append a Timeline entry to docs/KIRO_LOG.md in the format above (and update Metrics if they changed) before committing. Keep entries short (max ~8 lines).

3. Add a "How Kiro was used" section to README.md that summarises docs/KIRO_LOG.md in 5–8 bullet points and links to it. Do not change other README sections.

4. Make sure .kiro/ and docs/ are not in .gitignore.

5. Commit with the message "docs: add Kiro development log and steering rule". Do not push. Print the final KIRO_LOG.md.
````
